# Parts

零件資料的查詢與維護，是 MVP 的主體。

## 資料來源

公司既有的零件資料庫，在 SQL Server 上，Capture CIS 也在使用。

目前已知：

- 所有零件類型共用一張資料表，約 130 多個欄位。
- 用一個欄位區分零件類型（先前記錄為 `table_name`，值如 `R`、`C`、`L`、`IC`）。
- 資料庫上已有 trigger 記錄修改。

確切的表名、欄位名與型別尚未取得，見 [open-questions.md](../open-questions.md)。取得之前開發所用的假設記錄在 [parts-schema-assumptions.md](parts-schema-assumptions.md)。

## 原則

- 平台不更動零件庫的結構：不加欄位、不拆表、不建索引。
- 零件類型以資料庫中的類型欄位為準，平台不另外維護一份分類。
- 資料庫裡的零件資料是唯一來源，平台不複製一份。

## Model

一個 `Part` model 對應整張零件表，設定 `managed = False`，Django 不會為它產生 migration。

欄位定義由實際 schema 產生（`inspectdb`）後再整理。目前的 `Part` model 是依假設的結構手寫的。不為各零件類型建立個別的 model。

## Part Configuration

零件表有 130 多欄，但每種零件只用到其中一部分：電阻看阻值、誤差、功率；電容看容值、耐壓。Part Configuration 是每種零件類型一份的設定，內容包含：

| 設定 | 用途 |
|---|---|
| 類型代碼與顯示名稱 | 對應類型欄位的值，例如 `R` 顯示為「電阻」 |
| 列表欄位 | 表格要顯示哪些欄位、順序、標題 |
| 可搜尋欄位 | 關鍵字搜尋會比對哪些欄位 |
| 可篩選欄位 | 哪些欄位提供篩選 |
| 可編輯欄位 | 哪些欄位允許在平台上修改 |

設定寫在 `backend/apps/parts/configuration.py`。前端透過 API 取得設定後動態產生表格與表單，不在前端寫死欄位。

欄位的顯示名稱所有類型共用一份，個別類型可以覆寫，例如 `value` 在電阻顯示為「阻值」，在電容顯示為「容值」。

新增一種零件類型只需要加一份設定。

日後若需要讓管理者在網頁上調整設定，再把它搬進平台庫。

## 查詢

| API | 說明 |
|---|---|
| `GET /api/parts/types/` | 所有零件類型與各自的 Configuration |
| `GET /api/parts/types/{code}/filter-options/` | 該類型每個可篩選欄位目前有哪些值，供篩選選單使用 |
| `GET /api/parts/?type=R&search=...&ordering=...&<欄位>=...` | 列表，支援搜尋、篩選、分頁、排序 |
| `GET /api/parts/{id}/` | 單筆的完整資料 |

- `type` 必填。
- 列表只回傳該類型設定的列表欄位，加上 `id` 與備註欄位。
- 搜尋會比對該類型的可搜尋欄位，任一欄位包含關鍵字即符合，不分大小寫。
- 篩選是完全相等比對，只接受該類型的可篩選欄位。
- 排序只接受該類型的列表欄位，欄位前加 `-` 為遞減。未指定時依第一個列表欄位排序。
- 不在設定內的篩選或排序欄位回 400，不默默忽略。
- 一律分頁，預設每頁 50 筆，上限 200 筆。

### 前端

- 上方分頁切換零件類型，切換後搜尋、篩選、頁碼各自重置。
- 表格欄位、篩選選單都由 Configuration 產生。
- 點選一列會開啟側邊面板顯示該零件的完整資料，沒有值的欄位不顯示。

### 備註懸停

列表 API 的每一筆資料直接包含備註欄位，前端在滑鼠懸停於該列時顯示，不另外發請求。有備註的零件在料號旁有圖示標記。

## 編輯

| API | 說明 |
|---|---|
| `PATCH /api/parts/{id}/` | 修改單筆零件 |

- 需要 `parts.change_part` 權限，見 [auth.md](auth.md)。
- 只接受該類型設定中的可編輯欄位，其他欄位的修改會被拒絕。
- 驗證在後端執行，前端的檢查只是為了使用體驗。
- 修改與寫入修改紀錄在同一個 service 函式中完成。

### 與 CIS 並存

平台與 CIS 改的是同一張表。CIS 的使用方式與權限維持不變。

兩邊同時修改同一筆資料時，後寫入的會蓋掉先寫入的。MVP 的處理方式：送出修改時帶上讀取當時的值，後端發現資料庫中的值已經不同就拒絕並請使用者重新載入。

### 修改紀錄

平台用專用帳號寫入資料庫，所以既有的 trigger 記到的修改人會是那個帳號，而不是實際操作的人。

因此平台在平台庫自己記錄每次修改：

- 操作者
- 時間
- 零件識別
- 每個被修改欄位的舊值與新值

既有的 trigger 繼續運作，平台不依賴也不修改它。
