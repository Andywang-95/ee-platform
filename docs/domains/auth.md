# Authentication & Authorization

分成兩件獨立的事：

- 登入：這個請求是誰發的。
- 權限：這個人可以做什麼。

登入方式依環境不同而替換，權限邏輯不受影響。

## 登入

使用 Django 的認證後端機制，由環境變數決定啟用哪一種。同一時間只啟用一種。

| 方式 | 使用環境 | 使用者體驗 | 需要的條件 |
|---|---|---|---|
| 本地帳號 | 開發 | 輸入 Django 中建立的帳密 | 無 |
| 無感登入 | 公司（目標） | 開網頁即已登入 | 見下方 |
| AD 帳密表單 | 公司（退路） | 在網頁輸入 Windows 帳密 | 後端能連到公司 AD |

三種方式的結果相同：平台得到一個使用者名稱，並對應到平台庫中的一筆 Django User。第一次登入的使用者會自動建立，預設沒有任何編輯權限。

### 無感登入

使用者登入 Windows 後持有 Kerberos 票證。瀏覽器可以把票證交給內網網站，網站驗證後得知使用者身分，過程中使用者不需要輸入任何東西。這與在 SSMS 選擇 Windows 驗證是同一個機制。

驗證由反向代理負責。代理驗證通過後把使用者名稱放在 header 傳給 Django，Django 用內建的 `RemoteUserBackend` 接收。後端只接受來自代理的這個 header，不對外直接開放。

代理的做法取決於主機：

| 主機 | 做法 | 需要 IT 配合 |
|---|---|---|
| 加入網域的 Windows | IIS 啟用 Windows 驗證，再轉發到 WSL 內的服務 | 不需要另外申請 SPN |
| Linux，或未加入網域的 Windows | 支援 Kerberos 的反向代理，例如 Apache 加 `mod_auth_gssapi` | 服務帳號、`HTTP/<主機名稱>` 的 SPN、keytab |

瀏覽器端的條件：網站要被視為內部網路網站，瀏覽器才會自動送出票證。必要時由群組原則設定。

### AD 帳密表單

無感登入的條件無法滿足時使用。使用者在網頁輸入 Windows 帳號密碼，後端透過 LDAP 向 AD 驗證。平台不儲存密碼。

## 權限

使用 Django 內建的 User、Group、Permission，不自建權限資料表。

### MVP

| 權限 | 可以做的事 | 誰擁有 |
|---|---|---|
| （已登入） | 查詢零件 | 所有登入的使用者 |
| `parts.change_part` | 編輯零件 | 指定人員 |
| Django staff | 進入 Django Admin 管理權限 | 管理者 |

- 權限在 Django Admin 以個人為單位指派。Admin 同時就是 MVP 的權限管理介面，不另外開發。
- 每個請求即時檢查權限，權限變更後立刻生效。
- 前端依權限顯示或隱藏功能，但後端一定會再檢查一次。

### 之後

- 新功能各自定義權限，例如 BOM 工具的使用權。
- 人數變多時，用 Django Group 把權限打包成角色。
- 需要時把 AD 群組對應到 Django Group，讓部門成員自動取得權限。

## 與資料庫權限的關係

- 平台的權限與 SQL Server 的權限是兩回事。使用者在平台上能不能編輯，只由平台決定。
- 後端用一個平台專用帳號連資料庫，使用者不需要有 SQL Server 的權限也能使用平台。
- CIS 的使用方式與其資料庫權限維持原狀。
